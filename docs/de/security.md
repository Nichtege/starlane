# Sicherheit

Das System läuft mit deinen Benutzerrechten und liest deinen ganzen Vault. Deshalb gelten die Regeln unten. Die meisten sind durch Tests abgesichert (`tests/test_server.py`, `tests/test_routines.py`, `tests/test_scheduler.py`, `tests/test_agents.py`, `tests/test_agentdefs.py`, `tests/test_skills.py`, `tests/test_security_hardening.py`, `tests/test_peers.py`, `tests/test_notion.py`). Wo eine Regel von Claude Code abhängt und nicht von diesem Code, sagt diese Seite das.

## Was deinen Computer verlässt
- **Claude-Aufrufe schicken Text an Anthropic.** Jeder Lauf eines Agenten, eines Skills, von Atlas oder der Claude-Routine schickt seinen Prompt an die API von Anthropic: deinen Auftrag, den Gesprächsverlauf und alles, was Claude aus dem Vault liest, um ihn zu beantworten. Das tun nur Läufe, die du startest (oder planst).
- **Web-Agenten** schicken zusätzlich Suchanfragen und rufen URLs ab. Diese Anfragen und URLs erreichen Suchmaschinen und Webseiten. Die Regeln sagen dem Modell, keine persönlichen Angaben hineinzuschreiben; das ist eine Anweisung an ein Modell, keine Garantie.
- **Der Notion-Agent** schickt, sobald du ihn verbindest, was er liest und schreibt, an die API von Notion, für die Seiten, die du mit seiner Integration geteilt hast.
- Sonst lädt dieser Code nichts hoch. `git pull` (nur wenn eingeschaltet, siehe unten) spricht mit deinem eigenen Git-Remote.

## Was das System darf und was nicht
| Darf | Darf nicht |
|---|---|
| den Vault lesen | deine Notizen bearbeiten |
| in den Digest-Ordner schreiben (standardmäßig `AI/Digest/`: Digest, Vault-Check, datierte Tageskopien) und dort alte datierte Kopien löschen | etwas pushen, senden oder teilen |
| Zustand und Logs in `data/` schreiben; deine eigenen Agenten in `agents.local.toml` und `agents/local/` | eine Shell oder beliebige Programme starten |
| `aos setup` kopiert die Startdateien (Konfiguration, Routinen, Agenten, Skills, Doku, Demo-Vault) in deinen eigenen Ordner (standardmäßig `~/starlane` oder `$AOS_HOME`); `aos init <ordner>` legt einen kleinen Start-Vault an. Beide fügen nur Dateien hinzu, die es noch nicht gibt | |
| `git pull --rebase` im Vault, **nur wenn du diese Routine einschaltest**; es schreibt Dateien im Vault passend zu deinem Remote um, wie jeder Pull | |
| die Notion-Seiten ändern, die du mit dem Notion-Agenten teilst, **nur wenn du ihn verbindest** ([notion.md](notion.md)); eine löschen, nachdem du zugestimmt hast | in Notion auf eigene Entscheidung eines Agenten löschen |

Das System schreibt *mit den Standardeinstellungen* nie in `.obsidian/`: Es schreibt nur in den eingestellten Digest-Ordner. Zeigst du den Digest-Ordner woandershin, schreibt es dort; nichts hält eine Konfiguration auf, die ihn auf `.obsidian/` zeigt.

## Routinen
- `routines.toml` nennt nur **Namen** aus einer festen Liste. Ein Eintrag wie `command = "rm -rf /"` wird beim Laden der Datei abgelehnt.
- Ausgeführt wird immer `python -P -m aos <name>` als eigener Prozess, ohne Shell, mit `PYTHONSAFEPATH=1`: Eine Datei im Arbeitsordner kann nie ein Python-Modul überdecken. Die meisten Routinen nehmen keine Argumente; **Skill-Routinen** nehmen eine Skill-ID, einen Auftrag, ein Modell und einen Aufwand, alles beim Laden von `routines.toml` geprüft und als einzelne Argumente übergeben.
- **Zeitlimit** pro Lauf (`timeout_s`, höchstens eine Stunde): danach werden der Prozess und seine Kindprozesse beendet (Windows: `taskkill /T`; macOS und Linux: jeder Lauf führt eine eigene Prozessgruppe, und die ganze Gruppe wird beendet).
- **Tageslimit** (`max_runs_per_day`): Eine Schleife kann nicht den ganzen Tag laufen.
- **Sicherung** (`max_failures`): Nach so vielen Fehlschlägen in Folge ist die Routine gesperrt, bis du `python -m aos unblock <id>` ausführst.
- **Sperrdatei**: Zwei gleichzeitige Ticks starten dieselbe Routine nie zweimal.
- **Standardmäßig aus**: `git-pull`, die Claude-Routine und die Skill-Routine.

## Dashboard-Server (`aos serve`)
- Lauscht nur auf `127.0.0.1`, nicht in deinem WLAN und nicht im Internet. Dieser Wert ist absichtlich nicht einstellbar.
- Belegt den Port unter Windows exklusiv: Ein zweiter Server (oder ein anderes Programm) kann denselben Port nicht still übernehmen.
- **Startlink.** `aos serve` gibt `http://127.0.0.1:<port>/?k=<schlüssel>` aus (und öffnet ihn). Der Schlüssel ist zufällig, liegt nur im Speicher und ist bei jedem Start neu. Die Dashboard-Seite (`/`, `/index.html`, `/dashboard.html`) gibt es nur mit dem richtigen Schlüssel; ohne ihn kommt eine kurze 403-Seite, die auf den ausgegebenen Link verweist. Wo der Browser `Sec-Fetch-*`-Header schickt, gibt es die Seite außerdem nur bei einer Navigation auf oberster Ebene (`Sec-Fetch-Dest: document`, `Sec-Fetch-Site: none` oder `same-origin`); Anfragen von fremden und verwandten Seiten sowie Frames werden abgelehnt.
- Jeder API-Aufruf (Daten holen, eine Routine starten, einen Auftrag schicken) braucht das **Token** dieses Serverstarts (zufällig, in die Seite eingebettet, ungültig, sobald der Server stoppt).
- Der `Host`-Header muss auf jeder Route `127.0.0.1:<port>` oder `localhost:<port>` sein, auch auf `/` und `/healthz` (Schutz gegen DNS-Rebinding), und ein `Origin`-Header muss, falls vorhanden, zum Server passen (Schutz gegen fremde Webseiten). `/healthz` braucht weder Schlüssel noch Token und antwortet nur `{"ok": true}`.
- Nur Routinen aus `routines.toml` lassen sich starten, und nur über die Positivliste. Es gibt keine Dateiauslieferung nach Pfad und keinen Shell-Zugang über HTTP.
- Fehlermeldungen des Servers ersetzen die Pfade von Vault, Daten, Projekt und Benutzerordner durch Platzhalter (`<vault>`, `<data>`, `<project>`, `~`). Die Notizen eines Auftrags (zum Beispiel „could not start: ...“ vom Betriebssystem) siehst nur du, hinter dem Token, und sie können noch einen Pfad enthalten.
- **Content Security Policy**: Skripte nur mit einer Nonce pro Anfrage, kein Netzwerk außer dem Server selbst (`connect-src 'self'`), `frame-ancestors 'none'`; Inline-Styles sind erlaubt (`style-src 'unsafe-inline'`). Dazu `no-store` und `nosniff`.
- Daten aus dem Vault (Titel, Pfade) werden maskiert ins HTML eingebettet und im Browser nur als Text eingefügt (nie als HTML). Ein Titel wie `</script>` kann die Seite nicht übernehmen. Dasselbe gilt für die Texte der Oberfläche (`aos/locales/*.json`): Sie stehen maskiert als JSON in einem eigenen Skriptblock (`type="application/json"`), werden im Browser als Text eingefügt, und Texte im festen HTML der Seite setzt der Server HTML-maskiert ein.

## Agenten (`agents.toml`)
Du gibst einem Agenten einen Auftrag im Dashboard oder mit `aos agent <id> "..."`. Es gelten diese Regeln:
- **Nur lesend**: Werkzeuge kommen aus einer festen, eingebauten Liste: Vault (`Read`, `Grep`, `Glob`) und Web (`WebSearch`, `WebFetch`). Nennt `agents.toml` etwas anderes (Bash, Write, Edit, ...), wird die ganze Datei abgelehnt. Die eine Ausnahme ist `Notion` (siehe [Notion](#notion)).
- **Wo Claude läuft**: Agenten mit Vault-Zugriff (jeder mitgelieferte Agent) und Skills laufen mit dem Vault als Arbeitsordner; reine Web-Agenten und die eigenen Plan- und Prüfaufrufe von Atlas laufen in einem leeren Ordner, `data/agents/sandbox/` (frei von einer `CLAUDE.md`), sodass weder die Dateien des Vaults noch seine `CLAUDE.md` in ihrer Reichweite sind.
- **Das Lesen begrenzen die Berechtigungsregeln von Claude Code, nicht dieser Code.** Vault-Agenten bekommen `--allowedTools "Read(./**)"` und `--permission-mode dontAsk`: Claude Code erlaubt dann Lesen und Suchen im Arbeitsordner (und in Ordnern, die mit `--add-dir` hinzugefügt wurden; Skills fügen ihren eigenen Ordner hinzu) und lehnt alles andere ab. Das setzt voraus, dass Claude Code diese Regeln einhält und deine Einstellungen sie nicht erweitern: `--setting-sources user` hält die Einstellungen des Vaults draußen, aber deine Einstellungen auf **Benutzerebene** (`~/.claude/settings.json`: Allow-Regeln, Hooks) und deine Benutzer-`CLAUDE.md` gelten weiter. Leg dort keine breiten Allow-Regeln oder Hooks an, wenn du diese Grenze willst. Sind `Grep` oder `Glob` allein erlaubt, lässt Claude Code sie auch außerhalb des Arbeitsordners suchen; deshalb wird nur `Read(./**)` übergeben. Prüf das nach Updates von Claude Code erneut.
- **Vault und Web nur zusammen mit `mixed = true`, und mit einer Regel gegen das Hinaustragen.** Beim Laden wird ein Agent mit beiden Arten von Werkzeugen abgelehnt, außer er setzt `mixed = true`. Jeder mitgelieferte Web-Agent tut das, ebenso jeder Agent, den du im Dashboard oder mit `aos agent-new` mit Web-Zugriff anlegst: Alle Agenten lesen deine Notizen als Kontext. Eine präparierte Webseite könnte versuchen, so einen Agenten anzuweisen, Notizinhalte in eine URL oder Suchanfrage zu schreiben; die Laufzeit sagt `mixed`-Agenten, nie Notiztext, Notizpfade, Namen oder private Angaben aus Notizen in eine Suche oder URL zu schreiben, und setzt das außerhalb des Modells mit dem Web-Wächter (`aos/webguard.py`) durch: Ein PreToolUse-Hook, der jedem `mixed`-Lauf mit `--settings` mitgegeben wird, blockiert eine Suchanfrage oder URL mit acht aufeinanderfolgenden Wörtern einer Notiz, einer langen Zahl aus einer Notiz (in beliebiger Schreibweise) oder einem Geheimnis-Muster, auch URL-kodiert, als base64 oder hex. URLs aus Suchergebnissen, abgerufenen Seiten, Notizen und deiner eigenen Nachricht gehen durch; was du für den Lauf getippt hast, wird nie blockiert. Er schlägt geschlossen fehl (ein Fehler des Wächters blockiert den Aufruf). Er erkennt Notiztext, keine Umschreibung. Ein Agent, der deine Notizen nie sehen darf, wird von Hand als reiner Web-Agent eingerichtet (`WebSearch` und `WebFetch`, kein `mixed`). Weil Agenten sich auch gegenseitig Text weitergeben, wird Vault-Text an zwei weiteren Stellen von reinen Web-Agenten ferngehalten:
  - **Gespräche**: Geht die neue Nachricht an einen reinen Web-Agenten, fallen frühere Runden, deren Agent Vault-Zugriff hatte, aus dem Verlauf. Eine Runde zählt als Vault, wenn ihr Agent Vault-Werkzeuge hat (auch `mixed`), ein Skill ist oder nicht mehr existiert; eine Atlas-Runde zählt als Vault, außer jeder Spezialist, den sie nutzte, war ein reiner Web-Agent.
  - **Atlas**: Sobald der Gesprächsverlauf oder ein Bericht einer früheren Runde von einem Agenten mit Vault-Zugriff stammt, schreibt Atlas keine Aufträge mehr für reine Web-Agenten. So ein Agent bekommt stattdessen die ursprüngliche Frage (plus den vaultfreien Teil des Gesprächs), und die Begründung des Auftrags vermerkt das.
  - Was bleibt: Ein `mixed`-Agent bekommt nach deiner Wahl alles; die Schlussantwort, die Atlas schreibt, verbindet alle Berichte und wird dir gezeigt.
- **Restrisiken der Web-Agenten**: Suchanfragen und besuchte URLs verlassen den Computer. `WebFetch` kann grundsätzlich jede Adresse erreichen, die der Rechner erreicht, auch `localhost` und Adressen in deinem lokalen Netz. Web-Text ist Material, keine Anweisung, aber ein Modell kann sich trotzdem davon täuschen lassen. Antworten sind reiner Text, Markdown-Links darin sind im Dashboard aber anklickbar: Sieh dir einen Link an, bevor du ihn öffnest.
- **Agenten fragen einander** (`aos/peers.py`, Starlanes eigener MCP-Server über stdio, von jedem Lauf mit `python -I` gestartet): Ein Lauf, der zu einem Auftrag gehört, bekommt das Werkzeug `ask_agent`. Im Code durchgesetzt, nicht durch einen Prompt: Reine Web-Agenten fragen und antworten nicht (Vault-Text erreicht sie nie), niemand in der Kette wartender Agenten kann gefragt werden, höchstens zwei Ebenen und acht Nachrichten pro Auftrag. Der gefragte Agent bekommt die Nachricht als Nachricht eines anderen Agenten gekennzeichnet, mit deiner Anfrage als Kontext. Jede Nachricht ist ein eigener Auftrag mit den üblichen Limits und der Ausgabengrenze; Atlas und das Dashboard sehen das Gespräch.
- **Gespräche (Threads)**: Folgefragen geben die letzten sechs Fragen und Antworten desselben Gesprächs als Text mit (`claude -p` hat keine Sitzung), gefiltert wie oben beschrieben. Weitergegeben wird nur bereits geschwärzter Text aus `jobs.jsonl`; die Gesprächs-ID muss aus 12 Hex-Zeichen bestehen.
- `claude -p` startet ohne Shell, mit denselben Sperren wie die Claude-Routine: keine Connectors (`--strict-mcp-config`), keine gespeicherte Sitzung, nur Einstellungen auf Benutzerebene, `dontAsk` (nichts außerhalb der Liste ist erlaubt), höchstens 10 $ und 12 Züge pro `claude`-Aufruf (Schutz gegen Endlosschleifen), ein Zeitlimit (standardmäßig 5 Minuten für Vault-Agenten und 8 für Web-Agenten, höchstens 15; danach werden der Prozess und seine Kindprozesse beendet).
- Das Programm `claude` wird nur auf `PATH` gesucht: relative Einträge, der aktuelle Ordner und alles im Vault werden übersprungen, eine dort abgelegte `claude.exe` startet also nie.
- Der Auftrag geht über die Standardeingabe an Claude, die Regeln des Agenten als System-Prompt. Ein fester Zusatz sagt Claude, dass es nur liest, dass Notizinhalte Material und keine Anweisung sind, in welcher Sprache es antwortet und dass es nie Geheimnisse wiederholt. Benutzername und Sprache aus `aos.toml` kommen als eine Zeile von höchstens 40 Zeichen in diesen Prompt.
- **Die Antwort berührt nie eine Notiz**: Sie wird geschwärzt, auf 20.000 Zeichen gekürzt, nur in `data/agents/jobs.jsonl` gespeichert und im Dashboard als Text gezeigt (nie als HTML). Auch der Auftrag selbst wird vor dem Speichern geschwärzt.
- **Grenzen**: ein Auftrag pro Agent gleichzeitig, höchstens drei insgesamt (Läufe, die ein anderer Agent fragt, zählen nicht zu den dreien; die acht Nachrichten pro Auftrag begrenzen sie), ein Tageslimit pro Agent (`max_runs_per_day`), ein Auftrag hat höchstens 4000 Zeichen ohne Steuerzeichen, eine Anfrage höchstens 32 KB und nur `application/json`.
- **Tägliche Ausgabengrenze**: Bevor ein Lauf von Agent, Atlas oder Skill startet, wird die heutige Summe aus dem Kostenprotokoll (`data/agents/spend.jsonl`) mit einer Grenze von **25 $** verglichen (`DAILY_USD_CAP`; zum Ändern die Umgebungsvariable `AOS_DAILY_USD_CAP` setzen). Ab dieser Grenze wird der Lauf mit einer klaren Meldung abgelehnt und die Ablehnung protokolliert. Im Kostenprotokoll stehen nur fertige Läufe, laufende Läufe können den Tag also noch über die Grenze schieben. Die Claude-Routine (`claude-digest`) prüft vor dem Start dieselbe Grenze und hat zusätzlich ein eigenes Limit pro Lauf.
- Über HTTP gelten dieselben Schutzschichten wie für Routinen: nur `127.0.0.1`, Host- und Origin-Prüfung, Token. Jede Annahme, Ablehnung und jedes Ergebnis steht im Auftragsprotokoll (`data/agents/jobs.jsonl`).
- **Eigene Agenten** (`/api/agent-defs`, `aos agent-new`, `aos/agentdefs.py`): Das Dashboard kann Agenten anlegen, ändern und löschen. Das ist die einzige Schreibfunktion der Oberfläche, und sie ist eng begrenzt:
  - Geschrieben werden nur `agents.local.toml` und `agents/local/<id>.md`; `agents.toml` und alle Notizen bleiben unberührt. Die ID besteht nur aus `a-z`, `0-9` und `-`, ist nie ein Windows-Gerätename (`con`, `prn`, `aux`, `nul`, `com1`-`com9`, `lpt1`-`lpt9`), und der aufgelöste Pfad muss in `agents/local/` liegen.
  - Der Zugriff ist ein Schalter, *Vault lesen* oder *Vault und Web* (das setzt `mixed = true`), und wird in die feste Werkzeugliste übersetzt. Nur Web und jedes andere Werkzeug sind über Dashboard und Terminal unmöglich. Das Modell kommt aus der festen Liste; Zeit-, Tages- und Größenlimits gelten (höchstens 40 eigene Agenten, ein Prompt mit höchstens 6000 Zeichen).
  - Ein Prompt, der einem Passwort-, Token- oder Schlüsselmuster entspricht, wird abgelehnt (und der Wert nicht zurückgegeben). Steuerzeichen und ungültiges Unicode werden abgelehnt.
  - Schreibvorgänge nehmen eine Sperrdatei neben `agents.local.toml`, damit Dashboard-Server und `aos agent-new` im Terminal die Datei nie gleichzeitig neu schreiben (eine Sperre, die älter als eine Minute ist, gilt als Rest eines Absturzes). Nach dem Schreiben prüft dieselbe Ladefunktion wie beim Start die Dateien; schlägt sie fehl, wird der vorige Stand wiederhergestellt. Löschen wird abgelehnt, solange der Agent arbeitet. Die Datei wird komplett neu geschrieben: Kommentare in `agents.local.toml` bleiben nicht erhalten.
  - Token-, Host- und Origin-Prüfung gelten wie überall. Die Grenze bleibt ehrlich: Wer das Token hat, kann Agenten anlegen, die Aufträge mit einem Wortlaut und einer Beschreibung **seiner** Wahl ausführen, aber nie mehr als lesen und suchen.
- Unabhängig vom Planer: Aufträge schreiben nie in `state.json` und blockieren nie eine Routine. Stoppt der Server mitten in einem Auftrag, wird der Auftrag beim nächsten Start als fehlgeschlagen geschlossen.
- **Ehrliche Grenze**: Was im Vault steht, kann Claude lesen und in der Antwort zusammenfassen. Eine manipulierte Notiz kann die Antwort verfälschen, aber über dieses System nichts schreiben, senden oder ausführen. Wer das Token hat (siehe unten), kann Aufträge bis zu den Tageslimits auf deine Kosten starten.

## Notion
Die eine Ausnahme vom Nur-Lesen: nur wenn du sie einrichtest (`aos notion-connect`), für einen Agenten. Einrichtung und Benutzung: [notion.md](notion.md).
- Nur der Agent mit dem Werkzeug `Notion` bekommt Notion (höchstens ein solcher Agent, nie zusammen mit Web-Werkzeugen; das Laden lehnt beides ab). Er bekommt Notions offiziellen MCP-Server in einer festen Version: Das npm-Tarball wird gegen die sha512 von npm geprüft, die zwei Dateien, aus denen er läuft, per SHA-256, und die noch einmal vor jedem Lauf. Jedes Notion-Werkzeug ist erlaubt außer dem Löschen eines Blocks; `--strict-mcp-config` hält jeden anderen Server draußen.
- Der Token erreicht den Server nur über die Umgebung dieses einen Laufs, nie über eine Befehlszeile oder eine Datei, die die Werkzeuge des Laufs lesen können. Jeder andere Lauf startet ohne `NOTION_TOKEN` in seiner Umgebung.
- **Der Notion-Wächter** (`aos/notionguard.py`, ein PreToolUse-Hook, mit `--settings` übergeben) blockt das Löschen eines Blocks und jede Archiv- oder Papierkorb-Markierung auf true, egal wo im Aufruf, auch in einem JSON-String. Kann er nicht prüfen, blockt er. Der Agent stellt stattdessen eine Löschanfrage (`request_deletion`); Starlane fragt Notion nach echtem Titel und Link des Ziels und löscht erst nach deiner Zustimmung im Dashboard (`POST /api/notion/requests/<id>`, mit dem Token wie jeder POST) oder mit `aos notion-approve`. Eine Seite geht in den Papierkorb von Notion (30 Tage zum Wiederherstellen).
- **Ehrliche Grenzen**: Notion beschränkt die Integration auf die geteilten Seiten, aber darin kann der Agent Inhalte ändern und überschreiben, und Text in einer Seite kann versuchen, ihn zu lenken. Jeder Auftrag listet, was der Agent geändert hat (`notion_changes`); Notions Seitenverlauf ist das Rückgängig. Text in einer im Web veröffentlichten Seite ist öffentlich.

## Skills (`skills/`, `~/.claude/skills`)
Ein Skill ist Text, der als System-Prompt an `claude -p` geht. Deshalb:
- **Dieselbe Sperre wie bei Vault-Agenten**: nur `Read`, `Grep`, `Glob`, keine Connectors, keine Sitzung, `dontAsk`, 10 $ und 12 Züge, ein Zeitlimit (`[skills] timeout_s`, höchstens 15 Minuten), die tägliche Ausgabengrenze. Ein Skill kann sich keine weiteren Werkzeuge geben, auch nicht über sein Frontmatter.
- **Sein eigener Ordner ist zusätzlich lesbar** (`--add-dir`), damit seine Referenzdateien erreichbar sind. Beim Auflisten werden verlinkte Skill-Ordner (Symlink, Junction) übersprungen und verlinkte Dateien aus der Referenzliste weggelassen. Was Claude selbst im Vault und im Skill-Ordner öffnen darf, entscheiden die Berechtigungsregeln von Claude Code (siehe Agenten).
- **Modell und Aufwand** kommen aus festen Listen (`haiku`/`sonnet`/`opus`/`fable`, `low`/`medium`/`high`/`xhigh`/`max`; die Matrix auf der Startseite bietet nur Werte aus diesen Listen an). Freier Text wird mit 400 abgelehnt und kann nie als Kommandozeilen-Option gelesen werden.
- **Tageslimit pro Skill** (`[skills] max_runs_per_day`), ein Lauf pro Skill gleichzeitig, höchstens drei Läufe insgesamt (geteilt mit den Agenten).
- **Skill-Routinen** (`command = "skill"`) bleiben in der Positivliste: Skill-ID, Auftrag, Modell und Aufwand werden beim Laden geprüft und als einzelne Argumente übergeben, ohne Shell.
- **Ehrliche Grenze**: Skills aus `~/.claude/skills` können aus Plugins oder Synchronisierungen stammen. Ihr Text steuert Claude, nicht dein System: Sie können nicht mehr als lesen und antworten. Wenn du Skills von anderen hinzufügst, sieh dir vorher ihre `SKILL.md` an.

## Artefakte
- Inhalte werden **nur über IDs** ausgeliefert, die aus der Liste kommen (ein Hash aus Quelle und Pfad oder eine Auftrags-ID). Es gibt keinen Weg, einen Pfad zu übergeben. Verlinkte Dateien und Ordner sind ausgeschlossen, Größe höchstens 400 KB, höchstens drei Ebenen tief.
- Texte werden vor dem Anzeigen **geschwärzt**.
- **HTML-Artefakte sind fremder Inhalt**: Das Dashboard zeigt sie in einem `iframe` mit leerem `sandbox` (keine Skripte, keine Formulare, keine Verbindung zum Dashboard); der Rest der Seite fügt Titel und Texte nur als Text ein.

## Schwärzen und der Vault-Check
Das Schwärzen arbeitet mit Mustern und nach bestem Bemühen. Es ersetzt übliche Formen von Schlüsseln, Tokens und Passwörtern (API-Schlüssel mit bekannten Präfixen, Bearer-Tokens, Blöcke privater Schlüssel, Zeilen im Stil von `password: ...` und Ähnliches) durch `[redacted]` in Agentenantworten, Aufträgen, Digest-Auszügen und Artefakten. Ein Geheimnis, das keiner dieser Formen ähnelt, geht unverändert durch. `aos mapcheck` nutzt dieselben Muster, um Notizen zu melden, die Zugangsdaten zu enthalten scheinen (als **Fehler**; vom Wert wird nichts ausgegeben, nur seine Länge). Zugangsdaten gehören nicht in einen Vault; schreib das auch in die `CLAUDE.md` deines Vaults.

## Optionale Claude-Routine (`claude-digest`)
Standardmäßig aus. Schaltest du sie ein, startet sie `claude -p` im Vault mit: Modell Sonnet, höchstens 10 $ pro Lauf, keine gespeicherte Sitzung, keine Connectors (`--strict-mcp-config`), nur deine Einstellungen auf Benutzerebene (keine Einstellungen oder Hooks aus dem Vault-Ordner), nur die Lese- und Suchwerkzeuge (**kein Schreiben**, keine Shell, kein Internet) und `Read(./**)` als einzige Allow-Regel (mit derselben Abhängigkeit von Claude Code und deinen Benutzereinstellungen wie unter Agenten beschrieben). Die Datei `AI/Digest/weekly-review.md` (`[digest] review`) schreibt nicht Claude, sondern dieser Code: Er prüft die Antwort (nicht leer, höchstens 6000 Zeichen), schwärzt Geheimnis-Muster und setzt das Frontmatter selbst. Eine manipulierte Notiz kann also höchstens den Text dieses einen Entwurfs verfälschen. Ehrliche Grenze: Wird dein Vault mit Git synchronisiert, landet der Entwurf im Repository; lies ihn, bevor du ihm vertraust.

## Auf einem Server
Siehe [`vps-setup.md`](vps-setup.md): ein privates Netz (zum Beispiel Tailscale) statt einer öffentlichen Adresse, ein SSH-Tunnel zum Dashboard, eine Claude-Einstellungsdatei, die alles blockiert, was sendet, und Entwürfe statt Senden.

## Onboarding-Prompts
`python -m aos next` und [getting-started.md](getting-started.md) bieten Prompts zum Einfügen in Claude Code. Sie laufen in **deiner eigenen Claude-Code-Sitzung**, mit deren Rechten im Projektordner, nicht unter der Agenten-Positivliste oben: Claude kann dort Dateien bearbeiten und Befehle ausführen, so weit deine Claude-Code-Einstellungen es erlauben. Jeder Prompt bittet Claude, nichts zu pushen, zu veröffentlichen oder zu senden, deine Notizen nicht zu bearbeiten und jede Änderung als Diff zu zeigen und auf dein OK zu warten; das sind Anweisungen an ein Modell, keine Sperre. Lass die Berechtigungsabfragen an und lies die Diffs. `aos next` selbst prüft nur, ob Dateien existieren, liest nichts aus deinen Notizen und startet nichts.

## Ehrliche Grenzen
- Wer an deinem angemeldeten Konto sitzt, kann alles, was du kannst. Davor schützt das System nicht.
- Das Token steckt in der Dashboard-Seite, und die Seite braucht den Startschlüssel. Ein Prozess auf diesem Rechner, der deine Terminalausgabe, deinen Browserverlauf oder den Speicher des Browsers lesen kann, kann den Schlüssel finden; jeder Prozess, der `127.0.0.1` erreicht (auch andere Konten, WSL oder Container auf demselben Rechner), kann `/healthz` aufrufen und die API ohne Token versuchen. Deshalb lehnt der Server ausgeschaltete, gesperrte und ausgeschöpfte Routinen aus dem Dashboard ab: Über ihn ist nichts möglich, was `routines.toml` nicht ohnehin erlaubt.
- Vault-Check und Schwärzen erkennen bekannte Muster, nicht jedes mögliche Geheimnis.
- Die Lesegrenze von Claude-Läufen setzt das Berechtigungssystem von Claude Code mit deinen Benutzereinstellungen durch, nicht dieser Code.
